1Overview

NumaCore Lens is a single-page web app suite that delivers PCR-as-a-Service: predicting when major mining-equipment components reach end of life, scheduling their replacement, and managing the projects that execute the work.

What it is

Five panels (Pulse, Vitals, Horizon, Cadence, Deploy) hosted by Lens — the Mission Control shell. Lens loads Cadence and Deploy as embedded iframes; Pulse, Vitals, and Horizon render natively inside Lens itself. Three supporting tools (Intake, FleetConfig, Migrate) run standalone as data-prep utilities.

The whole suite is single-file HTML per tool. No server, no build step, no login. Opens from file:// or hosted on GitHub Pages — both first-class. Client data lives in a single [ClientCode]_fleet.json that never leaves the workstation.

What it isn't

  • Not licensed software. Tools are the internal delivery engine for the advisory service — never distributed to clients.
  • Not multi-user. One operator, one JSON file at a time. No concurrent editing.
  • Not a CMMS. Doesn't run work orders, doesn't dispatch crews, doesn't replace SAP/EAM. It schedules what should happen; SAP records what did happen.

The four pillars (what every feature must serve)

Pillar 1

Specialise deeply

Long-term component planning, reliability, sustainability. Not day-to-day dispatch.

Pillar 2

Productise the service

Defined scope, fixed retainer, repeatable delivery across multiple clients.

Pillar 3

Build annuity income

Recurring retainer base instead of single-client billable hours.

Pillar 4

Cross-client data moat

Every engagement adds to a benchmark dataset. Compounds. Eventually licensable.

Mission Control mental model

One JSON in at meeting start. Work happens across all five panels. One JSON out at meeting end. Children (Cadence, Deploy) broadcast snapshots on autosave; Lens swaps them into lensRawData and re-broadcasts to siblings. Each tool owns specific JSON slices and never writes outside its lane — see the Lens tab for the full slice-ownership rules.

3Lens — the Mission Control host

The shell that hosts the five panels and routes JSON between them. Loads Cadence and Deploy as iframes; renders Pulse, Vitals, and Horizon natively. Owns file I/O and the Config / Capability Gating layer.

Mission Control architecture in one paragraph

One JSON loaded at meeting start (Lens reads it). Children (Cadence, Deploy iframes) receive their copy via load-fleet postMessage — on first activation, on every tab re-activation, and (since v4.7) immediately when a new fleet file is loaded while embeds are open. Each child autosaves locally, then sends a fleet-updated message containing its owned slice; Lens allow-list-merges it into lensRawData. Siblings pick up the change on their next load-fleet re-push (there is no separate sibling-broadcast message). At meeting end, Save Final writes the consolidated JSON to disk via download.

Config + Capability Gating (CAPS)

Settings panel covers host-level config: terminology (termLabel: "Project" / "Shutdown" / "Outage"), theme, currency. The CAPS object exposes nine capabilities computed from the loaded JSON's contents:

  • SMU · Utilization · Benchmarks · MaterialMaster · IW39 · TLMaterials · ComponentPockets · PartsLibrary · ConMon

Each capability is "available" or "missing"; requiresCaps() drives the locked-but-visible UI pattern. Example: ConMon corner badges render "NR" until oil_samples[] arrives, then auto-light without a code change. Inspect via window.CAPS in DevTools.

CAPS is feature gating, not security

All nine capabilities are visible in the UI; missing ones are greyed with a tooltip explaining what data is needed. This is not access control — never describe it as one.

Idle % colour bands (v4.3.4 — Idle tiles)

Both idle tiles use the same monotonic palette per _idleBandClass: <30% green (healthy), 30–50% orange (caution), ≥50% red (concerning), null/no-data light grey + dimmed. Higher idle = worse.

Util % colour bands (v4.3.6 — operator-specified U-shape)

Util % uses a different palette per _utilBandClass — both extremes are orange because both under-utilisation and over-utilisation are concerns: <40% orange (under-utilised, fleet productivity gap), 40–70% blue (expected range), >70% orange (over-utilised, component stress), null/no-data grey. The "expected range" interpretation is operator-specific.

ConMon trend arrows (v4.3.1 — component cards)

Each component row in the drill-in shows a per-row ▲ ▬ ▼ trend arrow computed from the last 4 oil-sample sample_rank values via a slope classifier (_componentTrend). Slope > +0.5 = ▲ trending worse; < −0.5 = ▼ trending better; flat between. Heatmap cells use the same logic and clicking either surface opens the side-by-side sample-trend modal.

Visibility persistence — autosave to localStorage v4.3.5 + v4.3.6 FIX-1

The "fleets I've hidden" and "components I've hidden" toggles in the filter sidebar now survive a browser close, even if you don't click Save Final. v4.3.5 wired a debounced 400 ms write of ui_settings to localStorage['lens_ui_settings_<clientCode>'] on every visibility toggle. On the next file load, Lens checks if its localStorage entry is newer than the JSON's meta.lastSaved — if so, it overlays your in-session toggles on top of the file. A small gold pulsing ● dot next to SAVE FILE lights up while local changes are unsaved-to-file. When you click SAVE FILE, the JSON gets the new lastSaved stamp and the dot clears.

Per-client by design: localStorage is keyed by clientCode, so switching to a different client's JSON starts from that client's last localStorage state (or a clean slate if you've never opened them before). Same JSON loaded on a different machine = uses what's in the file (no cross-machine sync).

On overlay-apply, Lens fires a 2.4-second toast ("Restored unsaved visibility changes from date") so you know why the dot is lit. v4.3.6 FIX-1: numacore_lib.showToast's bottom: 24px was raised to 70px across the suite so the toast no longer visually collides with Lens's bottom-right #legend pill (the operator-reported dark-on-dark camouflage issue).

If you want to nuke the local cache

Open DevTools (F12) → Application → Local Storage → delete the lens_ui_settings_<CLIENTCODE> key. On next load Lens falls back to whatever the JSON says. A "Clear local cache" button in the Settings panel is on the deferred list — F12 works in the meantime.

Utilization rate (util_rate) — Data Editor + behaviour on file load v18.3

Every component has a util_rate (hours/day) that drives both the theoretical changeout date and the multi-cycle Projections feature. The value is stored internally as hrs/day (e.g. 18); operator views and edits it as a percentage of 24 hours (75%). Source path: Intake reads the XLSX % Util column at BUILD time, converts fraction × 24 → hrs/day, and writes it onto each component's util_rate field. UPDATE-mode refreshes the value when the source XLSX changes (e.g. quarterly review, shift-pattern change).

Util % column in Data Editor

Open the Data Editor tab. A column labelled Util % sits between Benchmark and % of Bench (drag to reorder; order is persisted in the JSON). Display shows the percentage form (util_rate / 24 × 100, e.g. util_rate 18 displays as "75"). Empty cell means util_rate is missing/zero.

Edit by clicking the cell, typing a new percentage value (0–100), and pressing Enter or clicking away. Internally, util_rate becomes typed_value × 24 / 100. Autosave fires within ~1.5s. Round-trip-safe.

Edit doesn't auto-trigger the file-load recompute — that runs only when a file is dropped. Projections refresh on next render of the Schedule tab (which reads r.util_rate live), but shadow/solid diamond positions stay until next file reload. Same pattern as other Data Editor edits (benchmark, install_hours, etc.).

Inferred util_rate warning (blue ⓘ badge)

When a V5 file has components missing util_rate, Cadence falls back to a unit-peer median: if at least 2 sibling components on the same unit have explicit util_rate, their median fills the gap for the missing components. Inferred components get a small blue ⓘ badge next to their label in the unit tree (hover for tooltip explaining the inference).

Inferred values produce sensible default predictions but are less precise than operator-set values. To replace an inferred value with an explicit one: edit the Util % column for that component in the Data Editor. The ⓘ badge disappears on next render (the inferred flag is cleared on explicit edit).

If NO components on a unit have explicit util_rate, none can be inferred — those components remain undateable until you populate util_rate (via Data Editor edit, or by re-BUILDing/UPDATEing in Intake with util_rate column mapped). Per PCR data-model rules: don't invent util_rate from calendar elapsed time; it's a measured/set value.

Auto-clear stale localStorage on rebuild

Cadence's autosave persists drag overrides and project edits in browser localStorage (scoped per client code). When you re-BUILD or re-UPDATE the fleet JSON in Intake, the new file represents a fresh starting point — old drag overrides from prior sessions should NOT bleed onto it.

v18.3 FIX-4 detects this automatically: on file load, Cadence compares the file's meta.lastSaved timestamp against the localStorage snapshot's savedAt. If the file is newer (i.e. Intake just rebuilt it), localStorage is cleared and a toast appears:

⚠ File is newer than local autosave — cleared stale N drag overrides + M projects (re-BUILD detected)

Round-trip safety preserved: when you Save File from Cadence, both the file and localStorage get the same timestamp → no clear on next load → mid-session drag work survives. If you want drags to persist across rebuilds, click Save File before rebuilding — that way the drags are in the JSON's componentDateOverrides and re-applied via the file (no localStorage dependency). DevTools console shows the exact timestamps and counts when a clear fires.

Category vocabulary unification v18.4 (Suite Chunk 5)

Cadence v18.4 was part of a suite-wide canonicalization sweep — the four tools + numacore_lib now share a single canonical 9-category vocabulary: engine, drivetrain, geared_drives, drill_rotary, hydraulics, cylinders, undercarriage, attachments, misc. Legacy aliases (tracks → undercarriage, drill_swing → drill_rotary) are normalised at read time via numacore_lib.canonicalCategory() so cross-tool data stays consistent regardless of which tool wrote it.

In Cadence specifically: every r.category is canonicalised on file load before the data drives Auto-Build / Components / Optimiser. The v17.x "misc-fallback rescue" pass was removed (categories should be canonical at the source after Intake — if something falls to misc, it's a real classification gap, not noise to be papered over). Side-effect you'll see: Undercarriage appears consistently as a category label across all four tools (no more "Tracks" in Cadence vs "Undercarriage" in Lens).

Bumping VERSION to '18.4' resets localStorage scope per the version-keyed pattern — your first load on v18.4 after upgrading from v18.3 starts a fresh autosave bucket. The file's componentDateOverrides still load normally; only the localStorage drag-pending state is reset.

Client setup — read this first

The header has three things that scope everything else in Intake to one client. Get these right at the start of each client engagement and the rest of the tool behaves consistently across sessions.

Workflow:

  1. Set your client code in the header first (this scopes the profile bucket).
  2. Drop your XLSX file. Click through to step 3 (Field Mapping).
  3. Map each column to a V5 field using the dropdowns.
  4. Click Save Profile, give it a name (e.g. "Monthly SMU export").
  5. Next time the same client sends the same file shape: drop the file, pick the profile from the dropdown on step 1, the mapping populates automatically.

Profiles are scoped per-client. Type a different client code in the header and you'll see THAT client's profile dropdown contents (different from the previous client's). The hint "for client: <CODE>" next to each profile dropdown surfaces this so you can always tell whose profiles are loaded.

Managing profiles at step 3

From v8.3 onwards, step 3 (Field Mapping) shows the full profile management UI — you no longer need to go back to step 1 to switch or delete profiles:

  • Loaded profile dropdown shows what's currently active. — No profile — means the current mapping was set manually or hasn't been saved.
  • 🗑 Delete button removes the selected profile from this client's bucket. The current mapping in the table is unaffected — you can save it again under a different name immediately.
  • Save Profile input pre-fills with the loaded profile name. Click Save to overwrite the loaded profile (you'll be asked to confirm). To save as a new profile, edit the name first.
  • Overwrite confirmation — if you type an existing profile name in the Save input and click Save, you get a popup confirming the overwrite. Cancel if you didn't mean to.

Renaming a profile (not a separate button — workflow): load the profile from the dropdown → type the new name in the Save Profile input → click Save → the old name's profile is still there → select it in the dropdown → click Delete. End state: same mapping, new name.

Why this is a separate mode (not part of UPDATE)

UPDATE merges new fleet-master data (SMU readings, component installs/changeouts, benchmarks) — those modify components[] / componentHistory[]. Keeping it on its own mode bar button means a "let's refresh idle figures this week" workflow doesn't risk re-running a full UPDATE.

Root cause: Host chrome wasn't aware of embed context.

FIX-3 — Horizon lifecycle / EOL reconcile

Symptom: Unit BD306 showed 52% lifecycle bar but 0 hrs EOL — those numbers can't both be right.

Root cause: Lifecycle bar used util_rate × 365 × 5 as denominator; EOL hours used expected_life_hours only. Two different denominators.

FIX-4 — workingData short-circuit on V4 Flat hybrid files Critical

Symptom: Open a V4 Flat file you know contains 27 projects, 1474 dates, 242 decisions. Cadence renders 0 projects, 0 dates, 0 decisions. Lens shows the same. Deploy works fine.

Root cause: Deploy v8 auto-creates an empty workingData stub on load. The V4 Flat file's real data lives under working. Cadence's read used "first truthy wins" (json.workingData || json.working || {}), short-circuited on the empty stub, and never reached the populated working block.

Two fixes, deliberately different:

  • Cadence v18 FIX-1 — Per-key fallback at the read site. Explicit probes for V5 envelope first, then V4, regardless of which is present. Defensive against all hybrid edge cases.
  • Lens v4.0 FIX-4 — Schema-anchored resolver (_readWorking()). Anchors on masterData presence to pick the right envelope; all call sites unchanged. Cleaner pattern for multi-call-site code.

Both patterns resolve the symptom. Cadence's is more defensive at the read site; Lens's is cleaner at the architecture level.

13Forecast Dates — how Cadence's changeout diamonds are calculated

The full lifecycle of a component's changeout date — from Intake UPDATE through to two weeks of Lens use. Calculations matter; this is the canonical reference for how the solid + shadow diamonds get their positions.

Primer — what the diamonds mean

Every component on the Cadence Schedule timeline has up to three diamond markers. Their position is computed from a single formula plus a small set of rules about who's allowed to move which diamond when.

Solid diamond
The working changeout date — what the planner uses. Stored as changeout_date.
Shadow (ghost) diamond
The current theoretical date. Only rendered when it differs from the solid. Stored as original_date.
Projection diamonds
Optional. v18.1 multi-cycle projection ON. Hollow markers at changeout_date + N × (benchmark / util_rate). Not persisted.
CM marker (variant)
A solid diamond on a condition-based component. Same position rules; different colour to flag the replacement strategy.
The three dates that drive everything

ERP changeout_date_erp — the source-system prediction at the time of Intake import. Never modified after Intake. Used as an anchor for delta detection.

SOLID changeout_date — the working date. May get dragged by the planner, anchored by a project link, or recomputed from the formula.

SHADOW original_date — the theoretical recompute. Tracks the formula's current answer on every JSON load. Used to render the ghost when it disagrees with the solid.

Worked example — Engine on BD401

Same component followed through all three stages. Real numbers. The same formula runs at every stage; what changes is which inputs are fresh.

Stage 4 — Long-term accumulation: orphan overrides & v18.5 visual indicators

Stages 1–3 cover one file load and a couple of weeks of use. This stage covers what happens over months — and how Cadence v18.5 surfaces it.

The accumulation problem

Every drag of a solid diamond, every project link Auto-Build creates, and every direct write to a component's changeout date adds an entry to the file's componentDateOverrides slot (or its V4-shape sibling componentDates). Once that entry is in the file, it is permanent — Intake's Update Everything deliberately preserves it (slice ownership; see callout below). Recompute correctly skips the solid-update for any component flagged in that slot — that's how dragging and project-anchoring are supposed to work.

Over months, the slot accumulates two kinds of entries: legitimate (tied to a project that is currently active — the solid genuinely should be held by the project bar) and orphan (entries from a drag the operator did once and forgot, or from a project that has since been edited, deleted, or re-linked elsewhere — the cause that created the override is gone, but the override entry survives forever).

A real example from the current file (audit 2026-05-14)

This operator file has 1,457 override entries. Of those: 306 are tied to currently-active project links (legitimate); 1,151 are orphans with no current project link (most are from early-product-use exploration drags that were saved to the file and never cleaned). About 1,000 are visibly diverged today; the other ~457 are silently overridden — solid happens to coincide with the recomputed shadow today, but they're locked from following the shadow if hours advance.

  • P (cyan italic, after the component name) → the component is in an active project's linkedIds. Hover for the project name + ID. The solid is held by this project's bar (Cause 2).
  • Lock (small amber padlock SVG) → the component has an override entry that is NOT explained by a currently-active project. Either Cause 1 (current intentional drag) or Cause 4 (orphan from past activity). Hover to see the solid date + the shadow date.

With the current operator file you'd see 306 P icons + 1,151 Lock icons + ~536 clean rows. The v18.4 asterisk-count was ~1,000 (visible-divergence-only); the v18.5 Lock count is higher (1,151) because it catches the ~400 invisible-orphans that are latent problems waiting to surface as hours advance.

Why Intake's Update Everything doesn't clean Cadence overrides — slice ownership

Each tool in the suite owns specific slices of the fleet JSON. Intake owns masterData (the equipment list, SMU readings, util_rate, idle %, last_read — the truth-from-ERP data). Cadence owns workingData.componentDateOverrides, workingData.projects, workingData.decisionLog (the planning work — the service deliverable). Other tools' slices are similarly partitioned.

When Intake does Update Everything, it deliberately preserves the Cadence working slice. Anything written into componentDateOverrides is sticky for the life of the file. This is correct behaviour — blowing it away on every monthly SMU update would erase the operator's planning work. The trade-off is that orphan overrides accumulate until something explicitly cleans them.

v18.5 surfaces the orphans via the Lock icon. The cleanup tools (audit panel + reconcile button) ship in a later version.

What v18.5.1 added — the cleanup toolkit

Same problem domain as v18.5, so this ships as a point release (v18.5.1) rather than a new minor version. Three new affordances, all paths converge on the same code (_resetOverride(id)):

  • Right-click "Reset" on any locked tree row. Single-component clear. Confirms in a dialog, snaps solid to shadow, Lock icon disappears. SAVE FILE to persist to the JSON.
  • Override Audit panel (Sketch 1) under ⚙ Config → Settings. Lists every override entry with All / Currently linked / Orphans filter chips. Sortable by Unit then Component. Per-row Reset button. Live count of total / linked / orphan.
  • Reconcile Orphans button (Sketch 2) in the same panel. Bulk-clears every orphan in one click after a count-preview confirm dialog. Appends a single summary entry to the Decision Log for forensic trail.

Nothing is destructive until you SAVE FILE — clean up freely in-memory, save when you're happy. The save path filters out cleared overrides automatically via the existing r.changeout_date !== r.original_date filter at L6654, so no special save-side code was needed.

What v18.5.2 added — the save-time safety net

The Sketch 3 investigation (2026-05-16) found that most lifecycle paths already have proper symmetric cleanup via the existing doLink → _preLinkDate save → breakLinkSilent restore pattern. Project deletes fan out through breakLinkSilent. Auto-Build uses doLinkSilent. The 1,151 historical orphans were most likely from pre-discipline state in earlier Cadence versions, not from a missing-cleanup bug in current code. v18.5.2 therefore doesn't add new prevention logic — it adds an observability layer.

Operator framing — why drag-without-project matters

Project / shutdown creation is the scheduling primitive in this suite. A component with shadow ≠ solid that isn't in any active project won't appear on the deployment schedule — it can't be deployed. Whether it's a historical orphan or an operator drag that never made it to a project, it's stranded. Manual drag is a legitimate first move, but it has to be followed up with a project assignment to enter the scheduling pipeline.

Concretely: every SAVE FILE click now fires a follow-up toast 1.8s after the "Fleet data saved" success message, telling you how many overrides aren't in any current project. "⚠ N override(s) not in any project — won't appear on the deployment schedule. Review via ⚙ Config → Override Audit → 🧹 Reconcile Orphans." Silent if zero. No auto-deletion — operator-controlled via v18.5.1's existing Reconcile button.

The detector reads from state.data directly (not from state.fileOverrideIds), so it catches BOTH file-loaded entries AND new drags / new project deletions made within this session. The count matches what will land in componentDateOverrides on this save (since the JSON save filter at L6654 uses the same r.changeout_date !== r.original_date predicate).

  • Auto-backup of the JSON before reconcile (file-system permission territory; v18.5.1 default is warning text only).
  • Provenance tagging on override entries (the rejected Option γ from v18.5.2 scoping). Would let cleanup distinguish "drag" from "project-write" definitively, but requires a schema field. Defer until v18.5.2's nudge proves insufficient.
  • Drag-time nudge (toast immediately after a drag if the component isn't in a project). Considered for v18.5.2 but deferred — save-time toast is less intrusive.

When in doubt

Why is the solid diamond not where the formula says it should be?

Check in this order:

  1. Is the component overridden? Right-click the diamond — if there's a "Reset to theoretical" / "Break override" option, it's in componentDateOverrides. The solid is frozen at your drag.
  2. Is it linked to a project? If the diamond sits exactly on a project bar's start date, the project anchor is winning. Right-click → "Break Link" to release it; on the next recompute the solid will move to the formula's answer.
  3. Is the shadow visible? If you see a ghost diamond next to the solid, the formula and the solid disagree — that's the signal that one of the above rules is in play.
  4. Check the delta flag. If |theoretical − ERP| > 60 days, the component is in state.deltaFlagged — Cadence surfaces these for operator review (filter chip / list).

Why did the shadow not move after an SMU update?

Most common cause: missing benchmark or zero util_rate — those components are skipped by the recompute (their original_date stays as-is). Look at the V5 Inferred util_rate blue ⓘ badge — if it's there for the unit, the component's util_rate came from the unit-peer median fallback, not an explicit value. If NO components on the unit have explicit util_rate, none can be inferred.

Why did ALL my dates jump after an Intake UPDATE?

Intake's UPDATE re-stamps changeout_date_erp if the source XLSX has a new ERP-predicted date. For components where changeout_date === original_date at the moment of UPDATE (planner hadn't dragged them), Intake also moves changeout_date with ERP — so the solid tracks the new ERP. For components you HAD dragged, Intake leaves the solid alone — on next Cadence load you'll see a ghost diamond appear next to the solid showing the new ERP delta. That's the intentional surfacing pattern.

I dragged a diamond and it sprung back next load — what happened?

The drag should have been written to componentDateOverrides via autosave (debounced 1.5s) — if Cadence wasn't on screen long enough after the drag for autosave to fire, the override might not have persisted. Also: the v18.3 FIX-4 auto-clear logic wipes localStorage drag overrides on file re-load if the file's meta.lastSaved is newer than the localStorage savedAt (Intake just re-built). Click SAVE FILE in Cadence after dragging to commit the override to the JSON before any rebuild.

Are projections persisted?

No. Projection diamonds (toggled via ◇ Projections) are pure render-time math — changeout_date + N × (benchmark / util_rate) out to the timeline edge, capped at 20 cycles. Nothing is written to the JSON. They don't appear in Auto-Build. Toggling them off hides them; toggling back on recomputes from current state.

What's the P next to some component names? What's the lock icon?

v18.5 visual indicators — see Stage 4 above for the full story. Quick version: P (cyan italic) = the component is currently linked to a project — hover to see which one. Lock (amber padlock) = the component has an override entry that's not tied to a currently-active project (either an intentional drag or an orphan from past activity) — hover to see the solid date vs. the shadow date. No icon = clean. The amber ✱ asterisk that used to fire on any divergent row in v18.4 has been retired — it had no tooltip and didn't distinguish between project-anchored (legitimate) and orphan-overridden (cleanup candidate).

How do I clean up the orphan overrides?

The cleanup toolkit has four paths now (v18.5.4), all safe (nothing persists until you SAVE FILE):

  • One row at a time — right-click any locked tree row → "Reset" → confirm.
  • Browse-and-clear single rows — click the 🔓 Override Audit tab. Filter by Orphans. Click Reset per row.
  • Multi-select bulk-clear (v18.5.4) — check per-row boxes, OR click a machine-header checkbox to select every component on that machine, OR a mix across multiple machines.   • Bulk clear all orphans — 🧹 Reconcile Orphans. Two-step confirm with count preview. Decision Log records the bulk action.

How do I navigate the Override Audit across a multi-fleet dataset?

v18.5.9 rebuilds the audit pane as a 4-level hierarchy matching the Cadence Schedule tree: Fleet → Model → Unit → Component. Each non-leaf level shows a chevron, tri-state checkbox, and rollup summary ("47 overrides · 12 linked · 35 orphan"). Click a row header to expand or collapse that level.

Roll-up counts are computed against the FULL override set, not the filter-restricted view. So under the Orphan filter, a fleet's rollup still reads "47 overrides · 12 linked · 35 orphan" — the filter only hides component rows that don't match, plus any empty groups above them.

Unit-level framing. Unit headers show "X of Y components" where Y is the FULL component count on that unit and X is the count with overrides. This lets you see at a glance whether a unit has a few stray overrides or wholesale divergence from the formula.

Tri-state checkboxes propagate down. Click the FLEET-level checkbox and every visible-leaf component under that fleet (across every model + unit) becomes selected. Click a single component to uncheck it and every parent level (unit / model / fleet) flips to indeterminate. Use this with Clear Selected for fleet-wide cleanup that's faster than per-row Reset but more focused than Clear All Orphans.

Expand All / Collapse All operate across every level at once. Collapse All leaves only the FLEET header rows visible — useful as a starting point for top-down navigation. Expand All opens everything.

The 🩺 Health Check button (from v18.5.8) still works the same way — it refreshes the underlying override set, and the new 4-level view re-renders against the fresh data.

How do I refresh the Override Audit during a working session?

v18.5.8 added a 🩺 Health Check button in the audit controls (row 1, next to Expand All / Collapse All). Click it any time to rescan the in-memory data and refresh the audit view to current runtime.

Why this button exists. The Override Audit reads from state.fileOverrideIds, a Set that's populated only when you LOAD a file. In-session changes — drags, project-link writes, breakLink restores, Auto-Build cluster applies — mutate the underlying records but don't touch that Set. Without the button, you wouldn't see new drags or new project links in the audit view until SAVE FILE + RELOAD. The Health Check button closes that gap on demand.

What it does. Sweeps every component in state.data, finds the ones where changeout_date ≠ original_date (real overrides), filters out today-clamp artefacts (so it stays consistent with the v18.5.6 save filter), and rebuilds state.fileOverrideIds from scratch. Re-renders both the audit table and the equipment tree (Lock icons). A toast confirms the result: "Health Check: 1,154 overrides now (+3 since last view)" or "Health Check: no change — still 1,151 overrides".

What it does NOT do. It doesn't modify any saved data. It doesn't clear anything. It doesn't persist anything to the JSON. It's purely a refresh of what the audit pane shows you. After clicking it, your next SAVE FILE will write exactly the same set of overrides it would have written anyway — the button reveals the current state, it doesn't change it.

Decision Log records each non-trivial Health Check click as type: 'override_health_check' with before / after / delta counts. Silent if nothing changed.

15Glossary

Vocabulary used across the suite. Alphabetical.

CAPS
The capability-gating object computed by Lens on load. Tracks 9 capabilities (SMU, Utilization, Benchmarks, MaterialMaster, IW39, TLMaterials, ComponentPockets, PartsLibrary, ConMon). requiresCaps() drives locked-but-visible UI. Inspect via window.CAPS. Not access control — feature availability only.
Changeout date priority
Override (advisor decision) > System-calculated (utilization profile) > ERP import date. ERP date stored as changeout_date_erp for reference only.
ConMon (Condition Monitoring)
Oil-analysis data ingested by Intake from FluidLife PDFs. Produces oil_samples[] records at JSON root. Each sample carries sample_rank (0–10), condition_band, concern_categories, flagged_tests[], wear metals, narrative finding.
Component pocket
A configured slot on a unit where a specific component installs. Defined in componentPockets[] per fleet/model/variant. Drives expected component complement on a unit. Editor pending (FleetConfig M2).
FLEET_IMAGE
Equipment-class → image-file mapping for the Vitals hero view. Falls back to a circle orb for unmapped classes.
Hybrid envelope
A JSON file with both V4 keys (working) AND V5 keys (workingData) at root. Usually because Deploy v8 auto-stamped an empty workingData stub on a V4 Flat file. Caused FIX-1 / FIX-4. Readers must use per-key fallback or schema-anchored resolution to handle this safely.
Intake
Standalone data ingestion tool. Three modes: BUILD (fresh client), UPDATE (merge), CONMON (oil samples). NOT a Lens panel.
Mission Control
The in-meeting workflow: Lens hosts Cadence and Deploy as iframes. One JSON in at start, one JSON out at end. State sync via postMessage.
oil_samples[]
Root-level array of ConMon samples. Each entry keyed by (unit_id, scope, target) where scope is component, system, or unit. Severity bands: Normal [0–5], Elevated (5–8], High (8–9], Very High (9–10].
PCR (Planned Component Replacement)
The advisory service. Predict when major components on heavy mining equipment reach end of life, build a rolling replacement schedule, manage execution. NumaCore Lens Suite is the delivery engine.
postMessage bridge
The host-child message channel between Lens and embedded iframes. Four message types: tool-ready, load-fleet, fleet-updated, request-save. (An earlier revision documented a fifth, refresh-fleet — it never existed in code; siblings sync via load-fleet re-pushes.)
Schema V4 Flat
The current production data format. Root-level components[], componentHistory[], working.{}. Auto-increment integer component IDs. Every running tool implements this. Stable.
Schema V5
The formal enterprise architecture target. Nested masterData / workingData / appState. Deterministic string component IDs ({floc_slug}_{component_name_slug}). New entities: componentPockets[], partsLibrary[]. Intake produces V5; no current tool reads V5 yet.
Slice ownership
The contract that each tool only writes specific JSON slices. Round-trip preservation through Mission Control depends on this. See the canonical table on the Lens tab.
SMU (Service / Machine Unit hours)
Total lifetime hours on a machine. Never resets except on capital replacement. Used to compute component accumulated hours: current_unit_smu − install_hours.
termLabel
The configurable label for "project" in Deploy: "Project" / "Shutdown" / "Outage". Set in ui_settings (Lens-owned). Affects every Deploy label.
util_rate
Average hours-per-day for a fleet / model / unit. Drives changeout-date forecasts. Stored at component level (Intake writes it on UPDATE) and at fleet/model level (FleetConfig M4).
