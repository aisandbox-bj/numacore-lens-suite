NumaCore Lens Suite

User Manual v1

Operator reference. Single-file, dark theme, offline-first. Updated 2026-05-08.

1Overview

NumaCore Lens is a single-page web app suite that delivers PCR-as-a-Service: predicting when major mining-equipment components reach end of life, scheduling their replacement, and managing the projects that execute the work.

What it is

Five panels (Pulse, Vitals, Horizon, Cadence, Deploy) hosted by Lens — the Mission Control shell. Lens loads Cadence and Deploy as embedded iframes; Pulse, Vitals, and Horizon render natively inside Lens itself. Three supporting tools (Intake, FleetConfig, Migrate) run standalone as data-prep utilities.

The whole suite is single-file HTML per tool. No server, no build step, no login. Opens from file:// or hosted on GitHub Pages — both first-class. Client data lives in a single [ClientCode]_fleet.json that never leaves the workstation.

What it isn't

  • Not licensed software. Tools are the internal delivery engine for the advisory service — never distributed to clients.
  • Not multi-user. One operator, one JSON file at a time. No concurrent editing.
  • Not a CMMS. Doesn't run work orders, doesn't dispatch crews, doesn't replace SAP/EAM. It schedules what should happen; SAP records what did happen.

The four pillars (what every feature must serve)

Pillar 1

Specialise deeply

Long-term component planning, reliability, sustainability. Not day-to-day dispatch.

Pillar 2

Productise the service

Defined scope, fixed retainer, repeatable delivery across multiple clients.

Pillar 3

Build annuity income

Recurring retainer base instead of single-client billable hours.

Pillar 4

Cross-client data moat

Every engagement adds to a benchmark dataset. Compounds. Eventually licensable.

Mission Control mental model

One JSON in at meeting start. Work happens across all five panels. One JSON out at meeting end. Children (Cadence, Deploy) broadcast snapshots on autosave; Lens swaps them into lensRawData and re-broadcasts to siblings. Each tool owns specific JSON slices and never writes outside its lane — see the Lens tab for the full slice-ownership rules.

Operator note

This manual is the operator memory aid (v1). Two copy-paste agent prompts in the Spin-off Prompts tab generate updated client-facing and future-operator variants when you need them — they re-read the suite's current state each time, so they don't go stale.

JSON-in JSON-out workflow

  1. Open Lens v4.0.html in a browser.
  2. Click Load Fleet → pick [ClientCode]_fleet.json.
  3. Work across Pulse / Vitals / Horizon / Cadence / Deploy panels. Cadence and Deploy autosave their slices into lensRawData via postMessage.
  4. Click Save Final at meeting end → browser download writes the updated JSON. Replace the file on disk.

Standalone tool use

Any of the four tools (Cadence, Deploy, Intake, FleetConfig) opens directly from disk and works without Lens. Detection is automatic: window.parent === window means standalone, otherwise embedded.

Backup discipline

Save final fleet JSON files to OneDrive (or equivalent) at meeting end. The JSON IS the session record — losing it means re-entering whatever was changed during the meeting.

3Lens — the Mission Control host

The shell that hosts the five panels and routes JSON between them. Loads Cadence and Deploy as iframes; renders Pulse, Vitals, and Horizon natively. Owns file I/O and the Config / Capability Gating layer.

Mission Control architecture in one paragraph

One JSON loaded at meeting start (Lens reads it). Children (Cadence, Deploy iframes) receive their copy via load-fleet postMessage on tab switch. Each child autosaves locally, then broadcasts a fleet-updated message containing its current snapshot. Lens swaps the snapshot into lensRawData and re-broadcasts to siblings via refresh-fleet. At meeting end, Save Final writes the consolidated JSON to disk via download.

Config + Capability Gating (CAPS)

Settings panel covers host-level config: terminology (termLabel: "Project" / "Shutdown" / "Outage"), theme, currency. The CAPS object exposes nine capabilities computed from the loaded JSON's contents:

  • SMU · Utilization · Benchmarks · MaterialMaster · IW39 · TLMaterials · ComponentPockets · PartsLibrary · ConMon

Each capability is "available" or "missing"; requiresCaps() drives the locked-but-visible UI pattern. Example: ConMon corner badges render "NR" until oil_samples[] arrives, then auto-light without a code change. Inspect via window.CAPS in DevTools.

CAPS is feature gating, not security

All nine capabilities are visible in the UI; missing ones are greyed with a tooltip explaining what data is needed. This is not access control — never describe it as one.

6Horizon

Long-range capital planning view. Today (v4-alpha): per-unit lifecycle bar + EOL hours. Chunk 10 brings the full capital-spend forecast chart.

v4-alpha placeholder

The Horizon panel currently ships as a scaffold only — header bar + a per-unit lifecycle grid. The capital-plan chart that integrates componentHistory[], costs[], and fleetPlan[] with projected dates from Cadence is the Chunk 10 deliverable.

What's shipped today

Three columns per unit: Unit, Lifecycle Bar (5-Year), EOL Remaining.

Lifecycle calculation

The lifecycle bar shows current SMU as a percentage of expected life. The denominator is computed in this priority order:

  1. masterData.units[].expected_life_hours if FleetConfig has set it
  2. Otherwise, util_rate × 365 × 5 as a 5-year fallback
lifecycle_pct = clamp(0..1, smu / horizonHrs)
EOL_hrs       = max(0, horizonHrs − smu)

Unknown horizon (no expected_life_hours, no util_rate) renders as — with a hint to set expected_life_hours in FleetConfig.

FIX-3 root cause

Earlier versions used different denominators for the lifecycle bar (util_rate × 365 × 5) and the EOL hours estimate (expected_life_hours only). Result: BD306 showing 52% bar but 0 hrs EOL. FIX-3 unified both onto the same priority order above.

7Cadence — the PCR scheduler

The biggest panel. Builds the rolling component-replacement schedule, runs the Project Optimiser, lays out resource loading, and exports to Excel. Standalone Cadence v18.html and embedded inside Lens via tools/cadence.html share the same code path — embed mode activates when window.parent !== window.

What you use it for

  • Drag-to-reschedule individual component changeouts on a Gantt timeline.
  • Cluster nearby changeouts into PCR projects (the "should we bundle these?" question).
  • See what each project costs against budget and resource headroom over time.
  • Auto-build a starting schedule from due-date forecasts when a fleet is new.
  • Export the whole schedule to Excel for distribution.

  • Resource LoadingCost / labour / equipment loading by month. Confirms whether the current schedule fits within budget and crew availability headroom before locking it in.

Embedded vs standalone

Cadence detects embed context with window.parent !== window. When embedded:

  • The file-load UI in the header is hidden (Lens handles file I/O).
  • JSON arrives via a load-fleet postMessage from Lens on tab switch.
  • Autosave broadcasts a fleet-updated message back to Lens after every change.
  • Saving is rerouted: clicking Save sends request-save to Lens, which writes the file.

Standalone behaviour is identical except the file-load UI is visible and Save writes directly via the browser download API.

Hybrid envelope readiness — FIX-1 / FIX-4 pattern

Cadence v18 reads JSON via per-key fallback (V5 envelope first, then V4 Flat) at every key — projects, decisionLog / decisions, componentDateOverrides / componentDates, etc. This handles hybrid files where Deploy v8 has stamped an empty workingData stub onto a V4 Flat file. If you see "0 projects" on a file you know has projects, it's almost certainly this — see the Troubleshooting tab.

11Migrate

One-way migration from V4 Flat to V5 schema. Sandbox tool — produces a candidate V5 file and an audit. Cutover is operator-driven; no current tool actually reads V5 yet.

Three-step wizard

  1. Drop your fleet JSON — V4 Flat file picker
  2. Audit — counts and issues table; severity badges (fatal / warn / info)
  3. Download migrated V5 file — only enabled when audit passes (no fatal issues)

Audit report

SectionWhat it checks
File infoFilename, size, declared schema, client code
CountsComponents, Component History, Projects, Component Date Overrides, Decisions, Oil Samples — before/after
IssuesSeverity-tagged list of anything migrate had to handle (deduped components, missing FKs, etc.)

What migration changes

  • Auto-increment integer component IDs → deterministic strings ({floc_slug}_{component_name_slug})
  • Flat root keys (components, working) → nested envelopes (masterData, workingData)
  • schemaVersion: 5 stamped (numeric)
  • FK-link audit: every reference resolved or flagged

What migration does NOT change

  • No data deleted. Every record carried forward.
  • workingData preserved verbatim.
  • No tool behaviour change — V5 readers don't exist in production yet.
Sandbox-only — DO NOT USE IN PRODUCTION YET

The migrator is validated end-to-end but no tool currently reads V5. If you migrate and then load the result into Lens / Cadence / Deploy, every panel will see "0 records" until V5 readers ship. Cutover timing is operator-driven; treat the V5 output as a snapshot, not a working file.

Idempotency

Running migrate on an already-V5 file is a no-op — the audit recognises the V5 envelope and produces an unchanged output.

12Troubleshooting

FIX-1 through FIX-4 root causes, common issues, rollback procedure. The hybrid-envelope FIX-1/FIX-4 history is non-obvious and worth knowing about — the symptom (0 projects on a file you know has projects) is misleading.

FIX history

FIX-1 — Iframe URL resolver 404 on GitHub Pages

Symptom: Lens deployed to GitHub Pages; clicking the Cadence tab shows iframe 404.

Root cause: EMBED_TOOL_URLS resolver used a pathname regex that worked on file:// but not over https.

Fix: Switched to a protocol check — window.location.protocol === 'file:' branches to relative paths; otherwise uses Pages-style absolute paths. Same fix applied to the openFleetConfig() launcher.

FIX-2 — Mission Control nesting chrome

Symptom: When Cadence/Deploy iframe is active, Lens's left fleet-filter column AND the header LOAD/SAVE FILE buttons are visible alongside the embedded tool's own header — duplicate, confusing.

Root cause: Host chrome wasn't aware of embed context.

Fix: _applyEmbedChrome(tab) hides LHS column + LOAD/SAVE buttons when target tab is iframe-embedded. Strip nav stays visible (it's how you switch back). Restored when switching to a native panel.

FIX-3 — Horizon lifecycle / EOL reconcile

Symptom: Unit BD306 showed 52% lifecycle bar but 0 hrs EOL — those numbers can't both be right.

Root cause: Lifecycle bar used util_rate × 365 × 5 as denominator; EOL hours used expected_life_hours only. Two different denominators.

Fix: Both now use masterData.units[].expected_life_hours if set, falling back to util_rate × 365 × 5. Single source of truth for both.

FIX-4 — workingData short-circuit on V4 Flat hybrid files Critical

Symptom: Open a V4 Flat file you know contains 27 projects, 1474 dates, 242 decisions. Cadence renders 0 projects, 0 dates, 0 decisions. Lens shows the same. Deploy works fine.

Root cause: Deploy v8 auto-creates an empty workingData stub on load. The V4 Flat file's real data lives under working. Cadence's read used "first truthy wins" (json.workingData || json.working || {}), short-circuited on the empty stub, and never reached the populated working block.

Two fixes, deliberately different:

  • Cadence v18 FIX-1 — Per-key fallback at the read site. Explicit probes for V5 envelope first, then V4, regardless of which is present. Defensive against all hybrid edge cases.
  • Lens v4.0 FIX-4 — Schema-anchored resolver (_readWorking()). Anchors on masterData presence to pick the right envelope; all call sites unchanged. Cleaner pattern for multi-call-site code.

Both patterns resolve the symptom. Cadence's is more defensive at the read site; Lens's is cleaner at the architecture level.

Rollback via archive snapshots

Every released version has a [BASE - pre-fix] snapshot in 4 - Build Output/archive/<Tool>/<version>/. To roll back:

  1. Locate the snapshot in archive/<Tool>/<version>/<Tool> <version> [BASE - pre-fix].html
  2. Copy it over the current 4 - Build Output/<Tool> <version>.html
  3. If the tool is also published as tools/<name>.html, replace that too
  4. Reload Lens — the rolled-back version takes effect immediately

Mid-version hotfixes preserve their pre-FIX snapshot in the same folder, e.g. Lens v4.0 [pre-FIX-4-workingdata-shortcircuit].html. Use the most specific snapshot that pre-dates whatever you want to undo.

14Glossary

Vocabulary used across the suite. Alphabetical.

CAPS
The capability-gating object computed by Lens on load. Tracks 9 capabilities (SMU, Utilization, Benchmarks, MaterialMaster, IW39, TLMaterials, ComponentPockets, PartsLibrary, ConMon). requiresCaps() drives locked-but-visible UI. Inspect via window.CAPS. Not access control — feature availability only.
Changeout date priority
Override (advisor decision) > System-calculated (utilization profile) > ERP import date. ERP date stored as changeout_date_erp for reference only.
ConMon (Condition Monitoring)
Oil-analysis data ingested by Intake from FluidLife PDFs. Produces oil_samples[] records at JSON root. Each sample carries sample_rank (0–10), condition_band, concern_categories, flagged_tests[], wear metals, narrative finding.
Component pocket
A configured slot on a unit where a specific component installs. Defined in componentPockets[] per fleet/model/variant. Drives expected component complement on a unit. Editor pending (FleetConfig M2).
FLEET_IMAGE
Equipment-class → image-file mapping for the Vitals hero view. Falls back to a circle orb for unmapped classes.
Hybrid envelope
A JSON file with both V4 keys (working) AND V5 keys (workingData) at root. Usually because Deploy v8 auto-stamped an empty workingData stub on a V4 Flat file. Caused FIX-1 / FIX-4. Readers must use per-key fallback or schema-anchored resolution to handle this safely.
Intake
Standalone data ingestion tool. Three modes: BUILD (fresh client), UPDATE (merge), CONMON (oil samples). NOT a Lens panel.
Mission Control
The in-meeting workflow: Lens hosts Cadence and Deploy as iframes. One JSON in at start, one JSON out at end. State sync via postMessage.
oil_samples[]
Root-level array of ConMon samples. Each entry keyed by (unit_id, scope, target) where scope is component, system, or unit. Severity bands: Normal [0–5], Elevated (5–8], High (8–9], Very High (9–10].
PCR (Planned Component Replacement)
The advisory service. Predict when major components on heavy mining equipment reach end of life, build a rolling replacement schedule, manage execution. NumaCore Lens Suite is the delivery engine.
postMessage bridge
The host-child message channel between Lens and embedded iframes. Five message types: tool-ready, load-fleet, fleet-updated, refresh-fleet, request-save.
Schema V4 Flat
The current production data format. Root-level components[], componentHistory[], working.{}. Auto-increment integer component IDs. Every running tool implements this. Stable.
Schema V5
The formal enterprise architecture target. Nested masterData / workingData / appState. Deterministic string component IDs ({floc_slug}_{component_name_slug}). New entities: componentPockets[], partsLibrary[]. Intake produces V5; no current tool reads V5 yet.
Slice ownership
The contract that each tool only writes specific JSON slices. Round-trip preservation through Mission Control depends on this. See the canonical table on the Lens tab.
SMU (Service / Machine Unit hours)
Total lifetime hours on a machine. Never resets except on capital replacement. Used to compute component accumulated hours: current_unit_smu − install_hours.
termLabel
The configurable label for "project" in Deploy: "Project" / "Shutdown" / "Outage". Set in ui_settings (Lens-owned). Affects every Deploy label.
util_rate
Average hours-per-day for a fleet / model / unit. Drives changeout-date forecasts. Stored at component level (Intake writes it on UPDATE) and at fleet/model level (FleetConfig M4).
